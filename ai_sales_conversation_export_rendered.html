用户提问 2

AI的大模型能否直接查询CK表，或者我有一个宽表，有销售id这个字段，然后根据API传参销售id=xxxx，来获取所有销售id=xxxx的行，来让大模型进行数据分析？

助手回复 2

可以，但不建议让大模型“直接裸连 CK/ClickHouse 表”。更推荐做成：

大模型 → 调用受控 API/工具 → 后端查询 CK → 返回结构化结果/摘要 → 大模型分析

你说的场景完全可行：宽表里有 sales_id 字段，API 传 sales_id=xxxx，后端查出对应行，再交给大模型分析。

推荐架构

用户问题
  ↓
大模型理解意图
  ↓
调用后端 API，例如 /sales/analyze?sales_id=123
  ↓
后端校验权限 + 查询 ClickHouse
  ↓
返回数据摘要 / 明细 / 聚合结果
  ↓
大模型生成分析结论

示例查询

假设表是：

sales_wide_table

字段包括：

sales_id
order_id
customer_id
amount
pay_time
region
product_name
status
...

后端可以执行：

SELECT *
FROM sales_wide_table
WHERE sales_id = {sales_id:String}
LIMIT 1000

然后把结果返回给大模型。

但要注意几个关键点

1. 不要让大模型直接拼 SQL 执行

危险写法：

SELECT * FROM sales_wide_table WHERE sales_id = '${user_input}'

如果用户传：

123' OR 1=1 --

可能造成 SQL 注入或越权查询。

应该使用：

  • 参数化查询
  • 白名单字段
  • 固定 SQL 模板
  • 权限校验

2. 不要无脑把所有行都塞给大模型

如果 sales_id=xxxx 命中几万行，直接传给大模型会有问题：

  • 超出上下文长度
  • token 成本高
  • 分析速度慢
  • 噪音多
  • 可能泄露敏感字段

更好的方式是后端先做聚合：

SELECT
    count() AS order_count,
    sum(amount) AS total_amount,
    avg(amount) AS avg_amount,
    min(pay_time) AS first_order_time,
    max(pay_time) AS last_order_time
FROM sales_wide_table
WHERE sales_id = {sales_id:String}

再补充必要明细样本：

SELECT order_id, customer_id, amount, pay_time, region, product_name, status
FROM sales_wide_table
WHERE sales_id = {sales_id:String}
ORDER BY pay_time DESC
LIMIT 100

这样大模型拿到的是“可分析的数据”，而不是原始大宽表全量 dump。

更合理的数据返回方式

可以让 API 返回这种结构：

{
  "sales_id": "123",
  "summary": {
    "order_count": 2580,
    "total_amount": 928300.5,
    "avg_amount": 359.8,
    "refund_count": 32,
    "active_customer_count": 760
  },
  "by_region": [
    {"region": "华东", "amount": 420000, "order_count": 1100},
    {"region": "华南", "amount": 280000, "order_count": 820}
  ],
  "recent_orders": [
    {
      "order_id": "A001",
      "amount": 560,
      "pay_time": "2026-05-01 12:30:00",
      "region": "华东",
      "status": "paid"
    }
  ]
}

然后大模型分析：

  • 该销售的总业绩
  • 区域分布
  • 客单价
  • 成交趋势
  • 异常订单
  • 退款情况
  • 客户复购
  • 与团队平均水平对比

典型实现方式

方式一：固定分析 API

适合业务明确的场景。

GET /api/sales/analysis?sales_id=123

后端固定查几个指标，返回给大模型。

优点：

  • 安全
  • 稳定
  • 可控
  • 性能好

缺点：

  • 灵活性较弱

方式二：大模型生成查询意图，后端转 SQL

例如用户问：

帮我分析销售 123 最近 30 天的成交趋势。

大模型输出结构化意图：

{
  "metric": "sales_trend",
  "sales_id": "123",
  "time_range": "last_30_days",
  "group_by": "day"
}

后端根据这个 JSON 生成安全 SQL：

SELECT
    toDate(pay_time) AS day,
    count() AS order_count,
    sum(amount) AS total_amount
FROM sales_wide_table
WHERE sales_id = {sales_id:String}
  AND pay_time >= now() - INTERVAL 30 DAY
GROUP BY day
ORDER BY day

优点：

  • 比固定 API 灵活
  • 比让模型直接写 SQL 安全

方式三：让大模型直接生成 SQL，但必须加防护

可以做，但要有：

  • SQL 只读账号
  • 禁止 INSERT/UPDATE/DELETE/DROP
  • 查询超时
  • 最大扫描行数
  • 最大返回行数
  • 字段白名单
  • 表白名单
  • SQL 审计
  • 权限过滤
  • 敏感字段脱敏
  • 查询成本控制

适合内部 BI 助手、数据分析 Agent。

关键结论

可以实现你说的：

API 传 sales_id=xxxx，查询宽表中所有 sales_id=xxxx 的行，让大模型分析。

但生产上建议这样做：

  1. 不要让大模型直接连 CK
  2. 不要直接返回所有明细行
  3. 后端先做权限校验、字段过滤、聚合计算
  4. 把“摘要 + 必要明细 + 统计指标”交给大模型
  5. 大模型负责解释、归因、洞察、生成报告

一句话：

CK 负责查数和聚合，大模型负责理解和表达；中间必须有一层安全可控的数据服务。
用户提问 3

如果我要让销售在跟AI对话时，可以选择几个预置功能：1-进行归因分析，2-生成分析报告，3-生成提案，怎么设计这个功能

助手回复 3

可以设计成一个 “销售 AI 分析工作台 / 对话式助手”，销售在对话里选择预置功能，大模型不直接查表，而是通过后端工具/API 获取数据、生成结果。

核心思路是：

销售选择功能 → AI 收集必要参数 → 后端查数/聚合 → AI 生成分析/报告/提案 → 用户可继续追问或导出

一、整体交互设计

销售进入 AI 对话后，可以看到几个快捷入口：

你好，我可以帮你做以下事情：

1. 归因分析
2. 生成分析报告
3. 生成客户提案

请选择一个功能，或直接输入你的问题。

也可以做成按钮：

[归因分析] [生成分析报告] [生成客户提案]

销售点击后，AI 进入对应流程。

二、功能 1：归因分析

目标

帮助销售分析：

  • 业绩增长/下降的原因
  • 客户流失原因
  • 转化率变化原因
  • 某个客户/区域/产品表现异常原因
  • 某销售 ID 下订单变化原因

交互示例

销售点击：归因分析

AI 问：

你想分析什么对象？

1. 我的整体业绩
2. 某个客户
3. 某个产品
4. 某个区域
5. 某个时间段的业绩变化

销售选择：

我的整体业绩，最近30天为什么下降？

AI 继续确认：

我将分析销售ID=123 在最近30天相较前30天的业绩变化，是否继续？

用户确认后，后端查询数据。

后端需要的数据

例如根据 sales_id 查询：

总体变化

最近30天GMV、订单数、客户数、客单价
对比前30天GMV、订单数、客户数、客单价

拆解维度

按客户拆

用户提问 4

这几个功能，是通过skill的方式实现么？

助手回复 4

可以用 skill 实现，但不一定只能用 skill。取决于你说的“AI 对话产品”运行在哪个体系里。

如果你是在 Genius Code / Claude Code 这类 Agent CLI/IDE 环境里做预置能力，skill 很合适。

如果你是在 面向销售的业务系统 / Web 对话助手里做产品功能，更推荐用：

前端预置入口 + 后端业务 API/Tool + LLM function calling / tool calling + Prompt 编排

也就是说，业务产品里通常不是直接叫 skill，而是叫 工具、函数、Agent Action、Workflow、Intent、Plugin。

1. Skill 适合什么

skill 更像是：

把某类可复用任务封装成一个“能力包”，里面包含 prompt、工具调用规则、流程说明、参数要求。

例如：

/sales-attribution
/sales-report
/sales-proposal

每个 skill 负责一个相对完整的任务流程：

  • 归因分析 skill
  • 分析报告 skill
  • 客户提案 skill

它可以定义：

  • 需要哪些输入参数
  • 如何调用数据查询工具
  • 如何组织分析逻辑
  • 输出格式是什么
  • 如何追问缺失信息

2. 但业务系统里更推荐分层设计

你可以这样理解：

用户点击功能入口
        ↓
意图识别 / 选择 workflow
        ↓
AI 按流程追问参数
        ↓
调用后端 API / Tool 查询数据
        ↓
AI 生成结果

这里的“skill”可以作为流程编排层，但不要让 skill 直接承担所有事情。

更合理的是：

Skill / Workflow：负责业务流程和提示词
Tool / API：负责查数、算指标、权限控制
LLM：负责理解、分析、生成

推荐设计

方案 A：用 Skill 封装三个功能

适合：

  • 内部 AI 助手
  • Agent 平台
  • 可配置技能市场
  • 需要快速上线 MVP
  • 每个功能流程比较独立

可以设计三个 skill：

sales_attribution_skill
sales_report_skill
sales_proposal_skill

归因分析 Skill

职责：

根据销售ID、时间范围、分析目标，调用指标查询工具，完成业绩变化归因。

调用工具：

get_sales_metrics
get_sales_dimension_breakdown
get_customer_changes
get_product_changes
get_conversion_funnel

输出：

1. 结论摘要
2. 核心变化
3. 主要归因
4. 证据数据
5. 建议动作

分析报告 Skill

职责：

根据销售ID、周期、报告类型，生成结构化经营分析报告。

调用工具：

get_sales_summary
get_trend_data
get_rank_comparison
get_customer_profile
get_risk_opportunities

输出：

1. 本期概览
2. 关键指标
3. 趋势分析
4. 客户分析
5. 问题与机会
6. 下阶段建议

客户提案 Skill

职责：

根据客户信息、历史交易、客户痛点和目标，生成面向客户的销售提案。

调用工具：

get_customer_profile
get_customer_order_history
get_product_recommendations
get_case_studies
get_price_policy

输出：

1. 客户现状
2. 业务痛点
3. 解决方案
4. 推荐产品/服务
5. 预期收益
6. 实施计划
7. 下一步沟通话术

方案 B：用一个 Sales Agent + 多个工具

适合更长期、可扩展的产品。

SalesAgent
 ├── attribution_analysis_tool
 ├── report_generation_tool
 ├── proposal_generation_tool
 ├── sales_data_query_tool
 ├── customer_profile_tool
 └── product_recommendation_tool

前端只是展示三个按钮：

[归因分析] [生成分析报告] [生成提案]

点击按钮后传入 intent：

{
  "intent": "attribution_analysis",
  "sales_id": "S123",
  "user_id": "U456"
}

Agent 根据 intent 进入不同流程。

这种方式更像业务系统里的标准做法。

我更推荐的落地方式

如果你是做销售业务场景，我建议：

预置功能不要直接等同于 Skill，而是设计成 Workflow。Skill 可以是 Workflow 的一种实现方式。

架构可以是：

前端按钮
  ↓
intent/workflow_type
  ↓
Workflow 编排层
  ↓
LLM
  ↓
Tool/API 层
  ↓
CK/CRM/订单/客户画像数据

示例：一次归因分析请求

前端发送：

{
  "workflow_type": "attribution_analysis",
  "sales_id": "S123",
  "user_input": "分析我最近30天业绩下滑原因"
}

后端 Workflow：

1. 解析时间范围：最近30天 vs 前30天
2. 校验销售权限
3. 查询总体指标
4. 查询客户维度拆解
5. 查询产品维度拆解
6. 查询区域维度拆解
7. 让 LLM 根据数据生成归因
8. 返回结构化结果

Tool/API 示例

不要只暴露一个万能 SQL 工具，建议暴露业务语义工具：

get_sales_kpi_summary
get_sales_trend
get_sales_dimension_breakdown
get_customer_churn_and_growth
get_product_performance
get_customer_profile
get_recommended_products
generate_proposal_context

例如：

{
  "tool": "get_sales_dimension_breakdown",
  "params": {
    "sales_id": "S123",
    "time_range": {
      "current": ["2026-05-01", "2026-05-30"],
      "previous": ["2026-04-01", "2026-04-30"]
    },
    "dimensions": ["customer", "product", "region"]
  }
}

三种实现方式对比

方式 适合场景 优点 缺点
Skill Agent 平台、内部助手、MVP 快速、可复用、流程清晰 容易和业务权限/数据层耦合
Workflow 正式业务系统 稳定、可控、可审计 开发成本略高
Tool Calling 灵活问答、复杂分析 可扩展、自然语言驱动 需要更强治理和安全设计

最佳实践建议

我建议你这样分：

Skill/Workflow：定义“怎么完成任务”
Tool/API：定义“能查什么数据、能做什么动作”
Prompt：定义“怎么分析和怎么表达”
权限系统：定义“谁能看什么”
前端：定义“用户怎么选功能”

不要这样设计：

一个 skill 里面直接写 SQL、查 CK、拼结果、生成报告

更推荐：

skill/workflow 调用 get_xxx_data API
API 内部查询 CK
LLM 基于返回数据生成分析

最终建议

如果你问“这几个功能是不是通过 skill 实现”：

可以。

但我建议更准确地说：

这三个功能应该设计成三个业务 Workflow；如果你的 AI 平台支持 Skill，那么每个 Workflow 可以封装成一个 Skill。
Skill 负责流程、Prompt 和工具调用策略；真正查 CK、查 CRM、算指标的部分应该放在后端 Tool/API。
